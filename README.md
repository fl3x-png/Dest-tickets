# Destination Tickets — этап 1

Для размещения по домену с HTTPS и общей PostgreSQL-базой подготовлена отдельная конфигурация `compose.production.yml`. Пошаговая инструкция: [deploy/README.md](deploy/README.md). Для публикации ещё нужны сервер и домен; локальная база автоматически не переносится.

Локальное приложение для команды Destination: вход, мероприятия, выдача именных билетов по одному или списком, реестр и повторное скачивание. Исходный каталог был пуст; готового MVP и исходного изображения билета не было.

## Что реализовано

- Удаление мероприятий администратором с подтверждением: мероприятие скрывается из рабочего списка, выдача новых билетов закрывается. Ранее выданные билеты, номера и история сохраняются в реестре. Физическое уничтожение данных не выполняется.

- FastAPI, Pydantic, SQLAlchemy 2, миграции Alembic. SQLite локально; PostgreSQL через переменную `DATABASE_URL`.
- React + TypeScript + Vite, Lucide, адаптивный интерфейс на русском. Собственный CSS без Tailwind/shadcn.
- Администратор создаёт и редактирует мероприятия, добавляет и отключает сотрудников, отменяет билеты. Менеджер просматривает мероприятия, выдаёт и скачивает билеты.
- Один запрос создаёт от 1 до 100 билетов. Независимый счётчик каждого мероприятия начинается с 0001. База атомарно резервирует диапазон номеров; уникальность `(event_id, number)` дополнительно обеспечивается ограничением БД. Отмена номера не освобождает.
- `Idempotency-Key` обязателен при выдаче; повтор с теми же данными и пользователем возвращает прежние билеты. Изменённые данные с прежним ключом дают 409. В браузере ключ сохраняется при повторе неудачного запроса до перезагрузки страницы.
- ReportLab: горизонтальный векторный шаблон, кириллица со встроенным TTF, адаптация размера длинного имени; отдельные PDF, общий многостраничный PDF и ZIP.
- Выдача проверяет генерацию PDF до фиксации транзакции. PDF повторно создаётся из сохранённого снимка мероприятия; последующее редактирование события не меняет старые билеты.
- Поиск ФИО без учёта регистра, поиск номера, фильтры мероприятия/статуса, страницы по 50 записей, CSV UTF-8 BOM с защитой от формул, журнал выдачи/скачивания/отмены.
- Пароли scrypt с солью, случайные серверные сессии (в БД хранится SHA-256 токена), HttpOnly/SameSite=Strict cookie, срок сессии, CSRF, проверка роли, ограничение входа в БД по логину/IP, CSP, запрет кэширования API. PDF не лежат в публичном каталоге.
- Модель Registration уже объединяет билеты одного запроса; поля будущей CRM предусмотрены. Добавление гостей к существующей регистрации, входная регистрация и розыгрыши относятся к этапам 2–3 и здесь отсутствуют.

## Запуск на Windows

Нужны Python 3.12+ и Node.js 22 LTS (Node необходим для изменения и пересборки интерфейса). Команды выполняются из каталога проекта.

```powershell
python -m venv .venv
.\.venv\Scripts\python -m pip install --no-cache-dir -r requirements.txt
Copy-Item .env.example .env
.\.venv\Scripts\python -m alembic upgrade head
.\.venv\Scripts\python -m backend.cli create-admin --username admin
.\.venv\Scripts\python -m backend.cli demo
.\.venv\Scripts\python -m uvicorn backend.app:app --host 127.0.0.1 --port 8000
```

Откройте http://127.0.0.1:8000. Пароль первого администратора вводится интерактивно дважды, минимум 12 символов. Пароли не передаются аргументами командной строки. Предварительная сборка `frontend/dist` включена в локальную поставку. Чистый архив проекта не содержит БД или учётных записей: создайте администратора командами выше.

Пересборка интерфейса:

```powershell
cd frontend
npm ci
npm run build
cd ..
```

Для разработки можно запустить `npm run dev` в отдельном окне: Vite перенаправляет `/api` на FastAPI :8000. При `COOKIE_SECURE=false` используйте только локальный loopback. Настоящие клиентские данные храните только после настройки HTTPS, резервного копирования и серверного доступа.

Шрифты: Windows использует Arial из `C:/Windows/Fonts`, Linux/Docker — DejaVu Sans. Можно указать `FONT_DIR` с `DejaVuSans.ttf`, `DejaVuSans-Bold.ttf`, `DejaVuSans-Oblique.ttf` и `DejaVuSans-BoldOblique.ttf`. Шрифты Microsoft не включены в архив проекта.

## Сценарий выдачи

1. Администратор создаёт мероприятие со статусом «Регистрация открыта».
2. Менеджер выбирает «Создать билеты», выбирает событие и вводит имена с новой строки.
3. Нажимает «Сформировать билеты», скачивает отдельные PDF, общий PDF или ZIP.
4. Чтобы зарегистрировать следующий список, нажимает «Новая выдача».
5. Повторное скачивание доступно в реестре. Администратор может отменить билет с подтверждением; PDF отменённого билета содержит отметку «ОТМЕНЁН».

Номер не является глобальным идентификатором: проверяйте пару мероприятие + номер. Адрес и время события показаны в PDF; время трактуется как местное время Казахстана (UTC+5). Время действий сохраняется в UTC и показывается в Asia/Qyzylorda.

## Тесты

```powershell
.\.venv\Scripts\python -m pytest -q
```

Тесты работают с отдельной временной SQLite БД и вымышленными данными. Проверяются нумерация, пакетная выдача, конкуренция менеджеров и одинаковых запросов, идемпотентность, права, CSRF, лимиты входа, вместимость, закрытая регистрация, отмена, неизменность данных старого PDF, Unicode, встроенные шрифты, поиск, CSV, PDF/ZIP. Проверка PostgreSQL и Docker отдельно необходима перед production.

## VPS и HTTPS

1. Установите Docker Engine/Compose и Caddy, направьте DNS домена на VPS.
2. Скопируйте исходный проект на сервер, создайте `.env` из примера, добавьте `POSTGRES_PASSWORD` со случайным паролем. Не коммитьте `.env`.
3. Выполните `docker compose up -d --build`. Приложение применяет миграции при запуске; для нескольких реплик запускайте миграции отдельной однократной задачей до старта реплик.
4. Создайте администратора: `docker compose exec app python -m backend.cli create-admin --username admin`.
5. Замените домен в `Caddyfile.example`, установите конфигурацию Caddy. Порт 8000 проброшен только на loopback; Caddy завершает HTTPS и направляет запросы туда.
6. В production cookie Secure включён Compose-конфигурацией. На HTTP с такой настройкой вход не работает — используйте HTTPS.
7. Резервируйте PostgreSQL: `docker compose exec -T db pg_dump -U destination destination > backup.sql`. Проверяйте восстановление на отдельной БД, ограничьте доступ к резервным копиям и задайте срок хранения.

API не доверяет X-Forwarded-For: за reverse proxy все запросы имеют общий IP-бюджет входа (50/15 минут), логин отдельно ограничен 10/15 минут. Для большой команды настройте trusted-proxy и IP rate limiting на proxy, не доверяя произвольным заголовкам клиента.

## Ограничения первого этапа

- PDF переработан по скриншоту пользователя: десять флагов, оригинальная фотография спикера и отдельные динамические надписи. Разрешение фото ограничено скриншотом, начертания системных шрифтов могут отличаться от исходного дизайна.
- Нет добавления гостей, check-in, розыгрышей, сущностей Prize/RaffleDraw, истории победителей и CRM-интеграций. Они намеренно отложены по требованию завершить первый этап отдельно.
- Поиск с Unicode выполняется в Python после чтения отфильтрованных билетов. Для больших реестров потребуется серверный нормализованный поисковый индекс.
- Присутствие в обзоре отмечено прочерком: данные этапа 2 ещё не собираются.
- При отмене ранее отправленный клиенту PDF не может быть отозван; реестр является источником актуального статуса.
- Для production ещё нужны проверка Docker/PostgreSQL, политика хранения персональных данных, эксплуатационный мониторинг и проверка резервного восстановления.
- Сессии и попытки входа сохраняются в БД; периодическую очистку истёкших записей следует добавить при эксплуатации.
- Идемпотентность после перезагрузки браузера требует повторного использования исходного ключа API. Не повторяйте выдачу вручную после сетевого сбоя, не проверив реестр.
